## Directory Structure
Each more than three level directories (e.g. `src/utils/example`) should have `index.ts`
`index.ts` should not have any logics, except aggregating (e.g. `export const output = { SomeClass, AnotherClass }`)
* src/fragments
  * Can nest other structure by prefixing `_`. examples: `_components`, `_providers`, `_utils`, `_types`
  * Can nest scope. Scope has same structure with src/fragments
    * Should has ScopeFragment.ts. examples: `fragments/users/UserFragment.tsx`
* src/repositories
  * Add database manipulation layers here.
  * Business logics should go to src/services
* src/services
  * Use other services or repositories to create use cases.
* src/types
  * Declare types here
  * For *.d.ts file, use src/definitions

* File names should name after the main export. (e.g. context.ts (x) buildContext.ts (o))
  * Use `index.ts` to make a convenient alias.

## Code Convention
* Do not make confusion by ambiguous naming.
  * Use kind instead of type
  * Use doc instead of document

* Complex state management should be done via providers, using `@/utils/context`
* Routes should be inside the `@/utils/routes`
* Styles should be done using tailwind
  * Use semantic colors
      * e.g. `--color-primary`, `--color-base-background`
  * Colors intended to be used for the background should have `-background` prefix.
      * e.g. `--color-base-background`, `--color-elevated-background`
  * But, if you have a color, which are intended to be used as both foreground and background, and you need a contrast color for that background, use `-foreground` prefix.
    * e.g. `--color-highlight`, `--color-highlight-foreground`
  * Avoid default colors (e.g. zinc, slate), in the component, as much as possible. Alternatively, create a semantic color alias for them in the @/styles/index.css
    * e.g. `--color-alert: var(--color-red-400)`
